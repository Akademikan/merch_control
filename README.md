# МерчКонтроль — автоматическая проверка фотоотчётов мерчендайзеров

Стартовый проект для ВКР (09.03.02). Что уже работает:

| Модуль | Файл | Состояние |
| --- | --- | --- |
| Чтение EXIF (время, GPS, устройство, ПО) | `app/services/exif.py` | готово, покрыто тестами |
| Расстояние до магазина (гаверсинус) | `app/services/geo.py` | готово |
| Проверки: место, окно визита, задержка загрузки, редакторы, устройства, скорость, дубликаты | `app/services/verify.py` | готово |
| pHash и расстояние Хэмминга | `app/services/duplicates.py` | готово |
| Решающий модуль (логистическая регрессия, 3 исхода) | `app/services/decision.py` | работает на стартовых весах, **веса нужно обучить на ваших данных** |
| Детектор товаров (YOLO), полнота выкладки Compl | `app/services/detector.py` | обёртка готова, **модель нужно обучить** |
| REST API (FastAPI) | `app/main.py` | готово |
| Telegram-бот приёма фото | `app/bot/telegram_bot.py` | готов, проверьте на своём боте |
| Обучение весов / детектора | `scripts/` | скрипты готовы |

Без обученного детектора система работает только по метаданным; как только появится `data/detector.pt`, API подхватит его сам.

## Быстрый старт (Windows / Linux / macOS)

```bash
python -m venv .venv
.venv\Scripts\activate            # Linux/macOS: source .venv/bin/activate
pip install -r requirements-dev.txt
python -m pytest                  # 23 теста должны пройти
copy .env.example .env            # Linux/macOS: cp .env.example .env
uvicorn app.main:app --reload     # API: http://127.0.0.1:8000/docs
python scripts/demo_request.py    # в другом окне: 4 тестовых фото и решения по ним
```

Ожидаемый вывод демо: нормальное фото — `accept`, другой город и вчера — `reject`, фото без EXIF — `manual`, повтор — `reject`.

## Как это устроено

```
Telegram / веб-форма ──► POST /visits/{id}/photos
                              │
              сохранить оригинал без перекодирования
                              │
        EXIF ─► проверки (место, время, дубликат, ПО, устройство, скорость)
        YOLO ─► найденные SKU ─► Compl = |S ∩ D| / |S|
                              │
        признаки x ─► p = σ(w0 + wᵀx) ─► accept / manual / reject + причины
                              │
                    БД (PostgreSQL) ─► панель супервайзера
```

Основные объекты: `Store` (магазин: координаты, радиус, часовой пояс), `Visit` (визит: окно времени, чек-лист SKU), `Photo` (фото с результатами всех проверок).

## Telegram-бот

1. Создайте бота у @BotFather, токен положите в `.env` (`BOT_TOKEN=...`).
2. Запустите API, затем `python -m app.bot.telegram_bot`.
3. В чате: `/visit 1`, затем отправьте фото **файлом** (скрепка → Файл).

Важно: если отправить фото обычным способом (как «сжатое»), Telegram удаляет EXIF. Бот всё равно обработает такое фото, но оно уйдёт на ручную проверку с пояснением. Это ключевой организационный вопрос ВКР: мерчендайзерам нужно отправлять файлом (или использовать отдельное приложение).

Время получения берётся из `message.date` (серверное время Telegram) — ему можно доверять больше, чем часам телефона.

## Что делать дальше (порядок для ВКР)

1. **Данные.** Выгрузить фото из чата(ов) с супервайзером, обезличить (лица, ФИО), завести справочник магазинов (координаты, радиус) и визитов.
2. **Настройка проверок на реальных снимках.** Подобрать `EPS_GPS_M` (допуск GPS) и `DUP_THRESHOLD`: посмотреть распределение расстояний `d` для заведомо честных фото.
3. **Разметка отчётов.** Для каждого фото решение супервайзера (`accept` / `reject`) — через `POST /photos/{id}/review` либо CSV. Этого же достаточно для обучения решающего модуля:
   `python scripts/train_decision.py --db sqlite:///./data/merch.db` (или `--csv`). Скрипт печатает ROC-AUC и рекомендуемые пороги `P_LOW` / `P_HIGH`; впишите их в `.env`.
4. **Детектор.** Разметить фото в CVAT/Label Studio (экспорт YOLO), положить в `data/yolo/`, запустить `scripts/train_detector.py`. Пример `data/yolo/data.yaml`:
   ```yaml
   path: data/yolo
   train: images/train
   val: images/val
   test: images/test
   names: {0: sku_cola_05, 1: sku_fanta_05}   # ваши SKU
   ```
5. **Чек-лист визита.** При создании визита передайте `required_skus` — `{"sku_cola_05": 2, "sku_fanta_05": 1}` (минимум фейсингов).
6. **Панель супервайзера** (пока нет): сделайте страницу над `GET /visits/{id}` (список фото, решения, причины, рамки детектора). Можно на Jinja/HTMX или React.
7. **Эксперименты для главы 6:** метрики детектора (P, R, mAP@0.5), метрики проверок на смоделированных нарушениях, ROC-кривая решающего модуля, доля автоматически закрытых отчётов.

## Известные ограничения и места для доработки

- Известные фото для проверки дубликатов берутся из всей таблицы `photos`; для большого объёма нужен индекс по хэшу или ограничение по датам.
- Обработка синхронная; для нагрузки вынесите `process_photo` в очередь (Celery/RQ).
- Текущий визит бота хранится в памяти; перенесите в БД или привязывайте визит автоматически по маршрутному листу.
- Веса решающего модуля по умолчанию — стартовые экспертные, а не результат обучения; в тексте ВКР опирайтесь только на обученные.
- Ultralytics распространяется под AGPL-3.0: упомяните это в работе или используйте Faster R-CNN из torchvision.
- Проверка «фото экрана» (муар) и планограммы (задача о назначениях) не реализованы.
- Тест `tests/helpers.py` генерирует синтетические JPEG; на реальных снимках с телефонов проверьте разбор EXIF (разные производители пишут GPS и время по-разному).
